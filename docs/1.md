**建議：繼續用「並行兩個 emitter」（JS + AS），共用 analyzer / AST。Porffor 而家唔適合作為主要 WASM 目標。**

### 簡短結論

| 方案 | 工作量 | 穩定性 | 控制力 | 適合你而家？ |
|------|--------|--------|--------|--------------|
| **並行兩個 emitter**（JS + AssemblyScript） | 中等 | 高（你完全控制） | 高 | ✅ **推薦** |
| **直接用 Porffor** 編譯而家產出嘅 JS | 極低 | 低（實驗性） | 低 | ❌ 而家唔建議做主路徑 |

### 為什麼 Porffor 而家唔適合做主目標

Porffor 係一個 **AOT JS/TS → Wasm / Native** 編譯器（由 Oliver Medhurst 開發），理念好吸引：

- 真正 Ahead-of-Time，輸出好細、記憶體好低
- 唔使帶成個 JS engine
- 最近開始可以跑一啲大型 framework 嘅基本功能

但實際限制仍然好大：

1. **仍然係實驗 / research 項目**  
   官方長期都講「not yet intended for serious use」，語言支援唔完整（很多 JS 特性仲未支援或支援不完整）。

2. **你個 runtime 同 Clojure 語意好難直接對上**  
   你而家嘅 emitter 產生大量 runtime helper（`truthy`、`hashMap`、`vector`、`invoke`、protocol、multi-arity、`recur` 等）。Porffor 未必能正確處理呢啲動態同自訂 runtime。

3. **相容性風險高**  
   今日可以 compile 嘅 code，Porffor 下次更新可能就 break。作為 compiler backend 會好被動。

4. **效能同功能取捨**  
   冇 JIT，長時間 hot loop 往往慢過 V8；同時一啲進階 JS 特性（closures、動態 object 等）支援有限。

簡單講：Porffor 好適合「把已經寫好、相對靜態嘅 JS 變成細 Wasm」，但唔適合做「Clojure 子集 → 可靠 WASM」嘅主要後端。

### 為什麼「並行兩個 emitter」仍然最穩

- **共用 analyzer + AST**：工作量已經被你而家嘅架構大大降低。
- **JS emitter 繼續保持正確性**（browser / Node 測試超方便）。
- **AS emitter** 專門為 WASM 服務，你可以逐步加 Value boxing → 之後再做 type specialization。
- 完全由你控制 runtime、protocol、collection 語意。
- 團隊已經熟悉 TypeScript → 寫 / 維護 AS emitter 學習成本最低。

呢個係典型 compiler 多 backend 嘅穩陣做法。

### 實用混合策略（推薦）

1. **主路徑（而家）**  
   並行兩個 emitter：
   - `emitter.ts` → JS（保持不變）
   - `emitter-as.ts` → AssemblyScript（用之前提供嘅骨架開始）

2. **實驗路徑（之後）**  
   當 JS 輸出已經穩定，可以試：
   ```bash
   porf wasm emitted.js out.wasm
   ```
   睇下有幾多可以成功 compile，作為額外 target 或效能實驗。唔好依賴它做 production。

3. **長期**  
   如果 Porffor 未來成熟到可以可靠處理你產生嘅 JS + runtime，可以再評估是否加第三個 backend。而家太早。

### 總結建議

- **主線**：繼續做並行 emitter（JS + AS），共用 analyzer/AST。呢個最穩、最可控、最符合「最低工作量但可靠去 WASM」嘅目標。
- **Porffor**：可以當有趣實驗或未來選項，但而家唔好押寶做主要 WASM 後端。
